# S3 — Hybrid retrieval SQL performance (pgvector)

Date: 2026-10-20 · Status: **done** · Scripts: `spikes/s3/` (throwaway) · Raw results: `spikes/s3/results-20000.json`, `results-200000.json`

## Decision

1. **MVP: no vector index.** Exact (brute-force) scan inside the tenant/profile filter is fast enough at personal-use scale (a few thousand units): ≤ 15 ms for ~7k matching rows when vectors are stored as `halfvec`.
2. **Store embeddings as `halfvec` with `STORAGE PLAIN`**, not `vector`. Same top-40 results (recall 1.0 / 0.999), 5× smaller than TOASTed `vector(1024)`, and exact scans are 3–5× faster. Re-check precision with real embeddings in S2.
3. **When an HNSW index is added, always run retrieval with `SET LOCAL hnsw.iterative_scan = relaxed_order`.** Without it, a filtered HNSW search silently returns too few rows: 14 of 40 for the big tenant at 200k units, i.e. a recall of 0.34. With it, the full 40 come back at recall ~0.96.
4. **Add HNSW (one partial expression index per embedding model) when** any profile has > ~10k active units **or** retrieval p95 exceeds 150 ms. The untyped column + `(embedding::vector(1024)) … WHERE embedding_model_id = N` index design from the plan works: the planner uses it.
5. **Hybrid query as planned** (semantic top-40 ∪ FTS top-40 → RRF top-30, one round trip) costs little beyond the semantic part. Use OR semantics for the FTS query (`websearch_to_tsquery('a or b or c')`), otherwise multi-term queries match almost nothing.

## Setup

- PostgreSQL 18.6 + pgvector 0.8.7, native Windows 11 on a laptop (i7-11800H, 16 GB), **default PG config** (`shared_buffers 128MB`, `work_mem 4MB`). Production with tuned memory will be faster, especially at 200k.
- Schema mirrors `docs/03-database-design.md`: `retrieval_units` (filters, generated `tsvector`, GIN) + `embeddings` (untyped `vector`, per-model partial HNSW expression index).
- Synthetic data: 200 topic clusters; embedding = cluster centroid + noise (1024 dims); text mixes cluster words with general vocabulary, so the semantic and lexical signals agree.
- Tenancy: 10 workspaces with 2 profiles each. Workspace 1 is "big" (~50% of rows); 9 "small" workspaces share the rest. Filters: workspace + profile + `is_active` + status (`verified|proposed|approved`).
- 50 queries (half on the big tenant), 1 warm-up pass + 3 timed passes; latency measured from PHP (execute + fetch). Recall is measured against the exact top-40.
- Per-query plans (`plan_cache_mode = force_custom_plan`), which matches Laravel's prepare-per-query behaviour (see "Pitfall" below).

| 20k units | ~6,800 | ~760 |

## Results — semantic top-40 (p50 / p95 ms)

| Mode | 20k big | 20k small | 200k big | 200k small | Rows returned (200k big) | Recall (200k big / small) |
|---|---|---|---|---|---|---|
| Exact, `vector` (TOASTed, default) | 44 / 68 | 7 / 11 | 1,799 / 4,335 | 415 / 2,471 | 40 | 1 / 1 |
| Exact, `vector` STORAGE PLAIN | 47 / 163\* | 3 / 5 | 406 / 464 | 118 / 138 | 40 | 1 / 1 |
| **Exact, `halfvec` STORAGE PLAIN** | **14 / 23** | **3 / 6** | 324 / 404 | 111 / 133 | 40 | 1 / 0.999 |
| HNSW, planner's choice, default settings | 42 / 65 | 7 / 11 | 11 / 20 | 150 / 225 | **14** | **0.34** / 1 |
| HNSW, `ef_search = 100` | 41 / 51 | 7 / 11 | 15 / 32 | 170 / 233 | 34 | 0.86 / 1 |
| **HNSW, `iterative_scan = relaxed_order`** | 40 / 55 | 7 / 11 | **18 / 28** | 166 / 239 | 40 | **0.96** / 1 |
| HNSW, `iterative_scan = strict_order` | 42 / 64 | 7 / 11 | 17 / 37 | 176 / 236 | 40 | 0.91 / 1 |
| HNSW forced, default settings | 1 / 2 | 1 / 2 | 12 / 19 | 11 / 20 | 14 (small: 1) | 0.34 / 0.03 |
| HNSW forced, `relaxed_order` | 7 / 12 | 46 / 70 | 18 / 30 | 55 / 124 | 40 | 0.96 / 0.90 |

\* noisy single outliers; p50 is the reliable figure.

How to read this:
- At 20k the planner never uses HNSW (rows identical to exact): an exact scan of ≤ 7k rows is cheaper.
- At 200k the planner picks HNSW for the big tenant (fast but short results unless iterative scan is on) and the exact path for small tenants (~7.6k rows, 110–170 ms on this untuned box). Forcing HNSW there trades recall 0.90 for ~3× speed, which isn't worth it at MVP scale.
- The 200k "exact, `vector`" row was measured with the table (2.6 GB incl. TOAST) far larger than `shared_buffers`. Part of that cost is memory, not CPU.

## Size and build cost

| | 20k units | 200k units |
|---|---|---|
| `embeddings` (`vector`, default TOAST) | 264 MB | 2,644 MB |
| `embeddings` (`vector`, PLAIN) | 158 MB | 1,575 MB |
| `embeddings` (`halfvec`, PLAIN) | 53 MB | 533 MB |
| HNSW index on `vector(1024)` | 156 MB | 1,563 MB |
| HNSW build (`maintenance_work_mem = 2GB`) | 11 s | 102 s |
| `retrieval_units` + GIN(tsv) | 13 MB + 1.6 MB | 131 MB + 13 MB |

Why `vector(1024)` is slow by default: each value is 4 KB, above the ~2 KB TOAST threshold, so Postgres stores it out of line in ~3 chunks. Every exact-scan row then costs several extra buffer reads (24k buffer hits for 6.8k rows in the 20k plan). `halfvec(1024)` is ~2 KB and fits in the row with `STORAGE PLAIN`.

## Pitfall found: generic plans for reused prepared statements

The first benchmark run reused one prepared statement per query shape. After 5 executions Postgres switched to a **generic plan** (planned without the actual workspace/vector), and the hybrid query with an HNSW index took 2+ s per call. Laravel prepares a fresh statement per query, so it always gets a custom plan. If we ever use persistent server-side prepared statements (connection pooler in session mode, long-lived workers with statement caching), set `plan_cache_mode = force_custom_plan` for the retrieval queries.

## Limitations

- Synthetic clustered vectors, not real embeddings. Recall figures are indicative, and the halfvec precision check must be repeated on real Voyage/OpenAI vectors in S2/M6.
- One laptop, default PG memory settings, Windows. Some 200k phases ran while the test suite was running in parallel, so treat ±20% differences as noise.
- Not measured: HNSW on `halfvec`, write/re-embed throughput, concurrent query load, `hnsw.max_scan_tuples` tuning.

## [VERIFY] items resolved

- pgvector ≥ 0.8 with `hnsw.iterative_scan`: available in 0.8.7, and it is required for correct filtered HNSW results (see Decision 3).
- Partial HNSW expression index on an untyped `vector` column (`(embedding::vector(1024)) vector_cosine_ops WHERE embedding_model_id = 1`): works, and the planner uses it.
